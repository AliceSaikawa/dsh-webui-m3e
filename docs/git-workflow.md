# Git の運用

このリポジトリ（`AliceSaikawa/dsh-webui-m3e`）で作業する人と AI エージェント（Claude Code、Codex、DSH など）の、worktree・ブランチ・コミット・PR・マージの決まりです。2026-10-16 に決めました。[設計書の README](design/README.md) や担当の設計書とここが食い違うときは、この文書を優先します。

## 0. 方針

- main へのマージは **squash merge** です。PR 1 本が、main の 1 コミットになります。
- 小さな PR をすぐ出し、マージしたらブランチを消します。
- push していないコミットの amend・rebase・並べ替えは、許可なしで行ってかまいません。
- 自分のブランチなら `--force-with-lease` を使ってかまいません。人と共有しているブランチでは許可を取ります。

squash では、ブランチのコミットは main に残りません。main の履歴に残るのは **PR のタイトルと本文** です。ブランチのコミットを整えるのはレビューを読みやすくするためで、main の履歴の質は PR のタイトルと本文で決まります。

### GitHub の設定（2026-10-16 に変更）

| 設定 | 値 | 意味 |
|---|---|---|
| `allow_squash_merge` | `true` | squash だけでマージする |
| `allow_merge_commit`、`allow_rebase_merge` | `false` | ほかのマージ方法は選べない |
| `squash_merge_commit_title` | `PR_TITLE` | main のコミットの件名は PR のタイトル（末尾に ` (#番号)` が付く） |
| `squash_merge_commit_message` | `PR_BODY` | main のコミットの本文は PR の本文 |
| `delete_branch_on_merge` | `true` | マージしたら、リモートのブランチを自動で消す |

ブランチ保護の必須チェックは `all checks` だけです。`strict`（最新の main を取り込み済みであること）は求めていません。

これより前のマージは merge commit で行っていました。そのため、main の古い履歴には `Merge pull request #…` と、ブランチの個々のコミットが残っています。

## 1. 操作と許可

| 操作 | 既定 |
|---|---|
| worktree・ブランチの作成、ローカルの編集と検証 | 依頼された作業の範囲で行ってよい |
| コミット | 依頼か許可があるときだけ |
| **push していない**コミットの amend・rebase・並べ替え | 行ってよい（許可は要らない） |
| 自分のブランチへの push | 依頼か許可があるときだけ |
| 自分のブランチへの `--force-with-lease` | push してよい作業なら、追加の許可は要らない |
| **共有しているブランチ**への `--force-with-lease` | 対象を示して許可を取ってから |
| `--force-with-lease` を付けない `git push --force` | 使わない |
| PR の作成・本文の更新 | 依頼か許可があるときだけ |
| main へのマージ | ユーザー、または対象の PR を示して許可された担当だけ |
| `git reset --hard`、コミットしていない変更を捨てる操作 | 使わない |
| マージ済みの自分のブランチと worktree の削除 | §9 の条件を満たせば行ってよい。満たさなければ確認する |

止められた操作は、別のコマンドや別のツールで回避しません。止めて、何が必要だったかを報告します。

### 自分のブランチと、共有しているブランチ

- **自分のブランチ**: いまの作業のために自分（同じ依頼を受けたセッション）が作ったブランチです。ほかの人やエージェントが push しておらず、自分以外の worktree でも checkout されていないものに限ります。
- **共有しているブランチ**: 上の条件のどれかに当てはまらないブランチです。例えば、ほかの人が push した、レビュー担当が修正を push した、ほかのエージェントの worktree がそのブランチを使っている、自分以外が作ったスタックの子がその上に載っている、などです。
- どちらか分からないときは、共有しているものとして扱います。

### force push の書き方

```bash
git push --force-with-lease --force-if-includes origin <ブランチ>
```

- `--force-if-includes` を必ず付けます。別の処理が裏で `git fetch` しても、取り込んでいないリモートのコミットを消さないためです。
- push が拒否されたら、リモートに知らないコミットがあるということです。取り込まずに上書きし直すことはしません。止めて、共有しているブランチとして扱います。

## 2. 作業場所（worktree）

1. 1 つの作業に、1 つの worktree と 1 つのブランチを使います。最新の `origin/main` から作ります。
2. 場所は `tmp/worktrees/<ブランチ名の / を - にしたもの>` です。`tmp/` は `.gitignore` に入っています。
   ```bash
   git fetch origin
   git worktree add tmp/worktrees/fix-issue-91-foo -b fix/issue-91-foo origin/main
   ```
   作ったら、その中で `pnpm install` を実行します。
3. 並行するエージェントには、それぞれ専用の worktree とブランチを渡します。1 つのブランチに書き込むのは 1 人だけです。
4. 無関係な変更が混ざった worktree は、直さずに切り出します。差分をパッチとして `tmp/` に保存し、新しい worktree で当てます。元の worktree の変更は消しません。
5. ユーザーが作業中の worktree（メインの checkout を含む）で、ブランチの切り替えや stash をしません。

## 3. ブランチ

- 名前は `<type>/issue-<番号>-<短い英語の名前>` です。Issue が無ければ `<type>/<短い英語の名前>` にします。type は §4 と同じ一覧から選びます。
  - 例: `fix/issue-79-draft-handoff`、`feat/issue-78-i18n-foundation`、`ci/pr-checks-e2e`
- 段階 2 の `feat/<設計書番号>-<名前>` は過去の名前です。新しくは使いません。
- 1 本のブランチ（1 本の PR）は、1 つの目的に絞ります。squash すると main の 1 コミットになるので、PR の粒度がそのままコミットの粒度になります。
- 途中で見つけた別の不具合（ルール・設計書・CI の不備を含む）は、別のブランチと PR で直します。

## 4. コミット

### ブランチの中のコミット

- ローカルでは気軽にコミットし、**最初の push の前に**、小さく順序だったコミットに整えます。
- 並びはレビューで読む順にします。例: 失敗する試験 → 修正、削除 → 作り直し、土台 → 機能。
- 1 本の PR に、別々に出せる目的のコミットが並んだら、PR を分けることを考えます。
- 直前のコミットに属する修正は amend（または fixup）にし、分けられるなら新しいコミットにします。
- **レビューが始まったあと**は、修正を新しいコミットとして積みます。レビュー担当が前回からの差分を追えるようにするためです。squash するので、main の履歴は汚れません。
- ブランチの先頭では `pnpm typecheck`、`pnpm test`、`pnpm build`、`git diff --check` を通します。
- 不要なコードはコメントアウトせずに消します。必要になれば履歴から戻します。
- 一時ファイル、ログ、画面写真、変異の確認用の変更はコミットしません（`tmp/` に置きます）。

### メッセージ

ブランチのコミットも、main に残る squash のコミット（PR のタイトルと本文）も、同じ形にします。

```text
<type>(<scope>): <subject in English>

<なぜ変えたか。件名の言い直しはしない>

AI-Harness: <DeepSeek Harness / Claude Code / Codex CLI など>
AI-Model: <モデル名>
AI-Effort: <推論の強さ>
AI-Duration: <例：15m>
AI-Cost: <分からなければ unknown>
AI-Task: <設計書の番号か Issue。例：08-settings>
```

- 件名は Conventional Commits の `type(scope): subject` です。type は `feat`、`fix`、`perf`、`refactor`、`docs`、`test`、`chore`、`ci` のどれかです。scope には変えた領域（`settings`、`composer` など）を書き、省略してもかまいません。
- **件名は英語**で、短い命令形にし、末尾にピリオドを付けません。変更の中心になる実在のシンボルがあれば、その名前を入れます。例: `fix(settings): keep pending drafts across reset`
- 本文には、理由とレビューで迷いそうな判断を書きます。件名を繰り返しません。本文の言語は日本語でも英語でもかまいません。
- 段落や箇条の途中で改行しません。1 文には 1 つのことを書き、言い換えずに実在の名前（シンボル、パス、コマンド）を使います。
- ブランチのコミットの本文には `#` で始まる行を書きません。エディタで `git commit` すると、git がコメントとして消すためです。
- AI が書いたコミットにはトレーラを付けます。分からない値は `unknown` と書きます。
- 個人情報、ローカルの絶対パス、認証値を書きません。

## 5. main への追従

- **PR を開く前**: 最新の `origin/main` に rebase します。検証を、本当の基準に対して行うためです。
- **レビュー中**: 基準（merge base）を動かしません。もう一度 rebase するのは、次のどれかのときだけです。
  - main と衝突した
  - main の変更がないと、このブランチの検証ができない
  - マージの直前に、同じファイルや同じ機能に関わる変更が main に入った
- 動かし方:
  - **自分のブランチ**: `origin/main` に rebase し、§1 の書き方で force push します。rebase のあとは検査をやり直し、レビュー担当に「rebase した。中身の変更はこれだけ」と伝えます（§8 の `patch-id` も使えます）。
  - **共有しているブランチ**: main をマージで取り込みます（force push はしません）。件名は `chore: merge main and resolve <衝突の内容>` のようにします。squash で main の履歴からは消えるので、マージのコミットが混ざってもかまいません。
- 設計書の「実装メモ」への追記どうしが衝突したら、main の節を先に、このブランチの節を後に置いて解消します。

## 6. PR

- レビューできて単独でマージできるまとまりができたら、すぐに PR を出します。大きな PR を 1 本出すより、狭い PR を数本出します。目安は数百行（試験を含む）です。千行を超えそうなら、分け方を先に相談します。
- PR はドラフトにせず、レビューできる状態で開きます。
- **タイトルが、main に残るコミットの件名になります。** §4 の形式（英語）で書きます。
- **本文が、main に残るコミットの本文になります。** 差分を持っているレビュー担当が 1 分で読める説明にします。作業の記録ではありません。次の節をこの順に置き、書くことのない節は消します。
  ```text
  ## Why
  <意図と方針を 1〜2 段落で>

  ## Scope
  - <変えた実在のシンボルとパス。名前を変えたなら新旧の両方>

  ## Tradeoffs
  - <レビューで聞かれそうな、選ばなかった案とその理由>

  ## Blast radius
  <何に影響し、なぜ安全か（または危ないか）を 1〜3 文で>

  ## Verification
  - <実際に流した方法と結果。例: `pnpm test` が成功、偽データの e2e の 08c が成功>
  - 確かめていないこと: <あれば>

  Closes #<番号>

  AI-Harness: ...
  AI-Model: ...
  AI-Effort: ...
  AI-Duration: ...
  AI-Cost: ...
  AI-Task: ...
  ```
  - トレーラは本文の **最後** に置き、前に空行を 1 つはさみます（git がトレーラとして読めるようにするため）。複数の AI やセッションが関わったときは、主に書いたものを書きます。
  - 全体を 40 行以内にします。超えそうなら削ります。
  - Scope はファイルごとの説明文にしません。実装の手順、レビュー指摘への対応の経緯、SHA の列挙、rebase の経緯、エージェントごとの報告、長いログや表も書きません。必要なら、ファイルや Issue のコメントにしてリンクします。
  - `## Summary` や `## Test plan` のような決まり文句の節は使いません。
  - Closes の行は Issue を閉じるときだけにし、関連を示すだけなら `Refs #<番号>` にします。
  - 本文は、レビューで変わった中身に合わせて、マージの前に直します。
- PR を開いたら URL を報告して、次の作業に進みます。CI の監視やマージは、頼まれたときだけ行います。

## 7. マージ

1. CI（`all checks`）が通っていること。ただし、CI が通っただけで安全とは見なしません。
2. 各 PR に、作った担当とは別のセッションのレビューがあること。blocking の指摘を直したら、マージの前にレビューか再確認を受け直します。
3. 最後に CI が走ったあとで main が進んでいれば、§5 の条件に当てはまるかを確かめます。当てはまれば main に追従し、検査をやり直します。
4. マージは squash で行います。
   ```bash
   gh pr merge <番号> --squash
   ```
   - 件名と本文は設定に任せ、`--subject` や `--body` で上書きしません。直したいときは、マージの前に PR のタイトルと本文を直します。
   - `--delete-branch` は付けません。ローカルのブランチを消そうとして、worktree で使っているブランチに当たると失敗するためです。リモートのブランチは設定で自動で消え、ローカルは §9 で片付けます。
5. マージするのは、ユーザーか、その PR について明示的に許可された担当だけです。

## 8. 依存する PR（スタック）

まず、スタックを作らずに済ませます。小さな PR はすぐ出してすぐマージするので、多くの作業は、前の PR のマージを待ってから main で始められます。待てないときだけ、ブランチを連ねます。

1. 子ブランチは親ブランチの先頭から作り、PR のベースを親ブランチにします。
2. スタックを rebase したり、ベースを変えたりするのは 1 人だけです。
3. 下から 1 本ずつマージします。マージ中のスタックには触りません。
4. 親が squash でマージされると、子には親の元のコミットが残ります（main の祖先にはなりません）。次のように直します。
   ```bash
   git fetch origin
   # <親ブランチ> は、マージされた時点の親の先頭（ローカルに残っているもの）
   git rebase --onto origin/main <親ブランチ> <子ブランチ>
   git push --force-with-lease --force-if-includes origin <子ブランチ>
   ```
   - 子の PR のベースは、親のブランチが自動で消されたときに GitHub が main に変えます。変わっていなければ `gh pr edit <子> --base main` で変えます。
   - 子が共有しているブランチなら、force push の前に許可を取ります（§1）。
5. rebase で SHA が変わっても、中身が同じなら前のレビューは有効なままにできます。中身が同じかは `git patch-id` で比べます。
   ```bash
   git diff <前の基準>..<前の先頭> | git patch-id --stable
   git diff origin/main...<子ブランチ> | git patch-id --stable
   ```
   値が違ったら、レビューを受け直します。
6. スタックは 3 本程度までにします。それ以上になりそうなら、分け方を相談します。

## 9. 後片付け

squash したブランチは main の祖先にならないので、`git branch --merged` ではマージ済みかどうか分かりません。PR の状態で判断します。

- **リモートのブランチ**: マージ後に GitHub が自動で消します。手元の参照は `git fetch --prune` で消します。
- **ローカルのブランチ**: 次のすべてを満たすときだけ、`git branch -D` で消してかまいません。満たさないときは止めて確認します。
  1. 自分のブランチである
  2. `gh pr view <ブランチ> --json state,headRefOid` で、`state` が `MERGED` である
  3. ローカルの先頭が `headRefOid` と同じである（マージのあとに積んだコミットがない）
- **worktree**: パスは `git worktree list` から取り、手では打ちません。コミットしていない変更があるもの、ほかのセッションが使っているものは消さずに確認します。それ以外は `git worktree remove <パス>` で消します（`--force` は付けません）。
